# GLEE 확장 구현 — 다음 LLM 리뷰·검증 인수인계

## 상태

- 사용자 요청에 따라 **리뷰와 검증을 실행하지 않았다.** 테스트, 빌드, 구문 검사, 브라우저 실행, 실제 노션 업로드를 하지 않았다.
- 구현 기준: GitHub `main`의 `e84b4981ec6c7059e2b6bb00bd20836af2970621`을 fast-forward로 반영한 `codex/glee-operations` 브랜치.
- 이 작업의 코드 변경은 로컬에 있으며 커밋·푸시·배포하지 않았다.
- 합의된 요구사항: `docs/2026-09-07-agreed-product-spec.md`. 이 문서보다 그 기획 문서와 마지막 사용자 지시가 우선한다.
- 실제 노션에 데이터베이스/속성/보기를 생성한 것이 아니다. 설정된 앱에서 첫 인증 요청을 처리할 때 준비 코드가 실행된다.

## 실행·연결 준비

실제 운영 노션 대신 **독립적인 검증용 부모 페이지와 검증용 장부**를 준비한다. 아래 명령은 인수인계용이며 이번 작업에서 실행하지 않았다.

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
$env:NOTION_TOKEN = '<검증용 integration token>'
$env:NOTION_PARENT_PAGE_ID = '<검증용 부모 페이지 ID>'
$env:NOTION_LEDGER_DATABASE_ID = '<기존 장부 형식을 복제한 검증용 DB ID>'
$env:SECRET_KEY = '<충분히 긴 임의의 문자열>'
$env:DB_PATH = 'review-cache.db'
.venv\Scripts\python -m app.main
```

- 기존 장부 기본값은 `4379fa3860c94a498dbae5e444dd9afd`. 반드시 검증 시 환경변수로 덮어쓴다.
- integration에 부모 페이지와 회계장부 모두 연결해야 한다. 콘텐츠 읽기·입력·수정 권한이 필요하다.
- 명단 파트: 소프라노/알토/테너/베이스/반주자/지휘자. 역할: 단원/파트장/지휘자. 행정 직군: 단장/홍보/총무 단일 선택.
- 활성 단장·총무는 각각 최대 1명이다. 중복이면 서버가 권한을 임의 부여하지 않고 설정 오류로 응답한다.
- API 설정이 없으면 운영은 503으로 차단한다. SQLite만으로 성공 응답하지 않는다.
- SQLite는 DB·보기 ID 캐시다. 노션이 원본이며 새 로그인 쿠키의 회원 ID도 Notion 페이지 UUID다. 예전 정수 ID 쿠키는 재로그인이 필요하다.
- 단일 프로세스·단일 worker로 실행한다. Notion의 복수 페이지 쓰기를 프로세스 내 `RLock`으로 직렬화한다. 다중 worker로 확대하기 전에 분산 잠금/동시 수정 정책을 별도로 검토해야 한다.
- 프런트는 빌드 없는 ES modules다. 기존 로고와 Figma 에셋을 그대로 사용한다.

## 권장 리뷰 순서

1. 기획 문서의 각 조항을 서버 권한과 실제 화면에 연결한다. 버튼 숨김뿐 아니라 직접 API 요청도 확인한다.
2. 노션 속성 타입, 관계 ID, 파일 객체 인코딩을 확인한다. 기존 장부 수식·옵션을 훼손하지 않는지 확인한다.
3. 학기 전환·출석 마감·취소·파일 업로드의 중간 실패와 재시도를 먼저 확인한다.
4. 로그인 사용자 전환·역할 변경·stale 상태에서 타인의 데이터나 편집 권한이 남지 않는지 확인한다.
5. 모바일에서 긴 제목, 5개 탭, 달력, 사진, 곡 선택 창, 긴 금액이 정상 표시되는지 확인한다.

## 자동 검증을 추가할 지점

기존 `tests/`는 SQLite/마감 후 일괄 동기화 구조의 테스트다. 새 기본 경로에 그대로 적용하면 다른 동작을 기대할 수 있다. 기존 테스트 통과만으로 이번 기능을 검증했다고 판단하지 않는다.

- 새 `OperationsStore` fake를 만든다: `bootstrap`, `read`, `roster`, `save`, `delete`, `upload`, `ensure_semester_views`, `lock`, `ledger_categories`를 구현한다. 명단에는 일반 단원, 4개 파트장, 반주자, 지휘자, 단장, 홍보 2명, 총무를 준비한다.
- `Operations` 단위 테스트에서 시간은 `db.now_kst`를 고정한다. HTTP 테스트는 `app.state.operations`의 store를 fake로 주입한다.
- SDK 경계 테스트는 `notion-client`와 `httpx` 응답을 모킹한다. 실제 API 계약 확인은 검증용 노션에서 별도 수행한다.
- 선택된 저장 호출 N번째에 예외를 발생시키는 fake를 만들어 모든 복합 동작을 재시도한다.

다음 명령도 **실행 예정 예시**다.

```powershell
.venv\Scripts\python -m compileall app
.venv\Scripts\python -m pytest --basetemp=.pytest_tmp
node --input-type=module --check < app/static/operations-ui.js
```

PowerShell에서는 마지막 표준입력 리다이렉션 예시 대신 JS 파일 내용을 Node의 표준입력에 전달하거나 적절한 셸에서 실행한다. JS imports까지 확인하려면 실제 브라우저 모듈 로딩을 추가한다.

## 필수 동작 시나리오와 기대 결과

### 권한·명단

- 일반 단원: 출석/일정/재정 조회. `/api/materials/{id}/open`, 자료 수정, 회계 수정은 403.
- 파트장 + 총무: 지휘 탭과 회계 편집 모두 가능. 다른 파트 출석 수정은 403.
- 반주자: 본인 출석 + 지휘 자료 확인 가능. 출석 현황 관리 불가.
- 홍보: 모든 일정 사진 관리 가능, 행정 일정 생성/수정/삭제는 403.
- 단장: 행정 탭 및 출석 탭에서 행정 일정 생성 가능. 지휘 일정 수정은 403.
- 지휘자: 연습·정기공연·외부공연 관리 가능. 출석 본인 입력/자동 결석 대상에서 제외.
- 노션에서 역할을 교체하고 새로고침: 현재 담당자가 과거 학기에도 같은 관리 권한을 가짐. 기존 작성자·확인자 기록은 유지.
- 로그인/로그아웃, 기존 정수 쿠키, 비활성 회원, 중복 단장·총무, 다른 origin에서의 POST 요청을 확인한다.

### 일정·사진

- 첫 화면: 오늘+미래의 지휘/행정 일정 날짜순. 여러 날의 진행 중 행정 일정은 위에 표시. 과거/취소 일정은 제외.
- 캘린더: 지난 일정, 정기/외부공연 강조, 다일 행정 일정의 모든 날짜 표시.
- 날짜에 1개면 바로 상세, 2개 이상이면 해당 날짜 목록 → 상세. 0개면 빈 목록.
- 연습·공연은 하루+시작 시각 필수. 행정은 종일·다일 가능. 설명은 전체 공개.
- 단장/홍보 누구든 사진 1장이면 일정 전체 의무 충족. 다일 일정도 1장.
- 종료 당일에는 미등록 경고 없음, KST 다음 날부터 시작 화면+행정 탭 느낌표+개수 배지.
- 다른 홍보가 올린 사진 교체/삭제 가능. 전부 삭제하면 기한이 지난 일정의 경고가 재개.
- 사진 교체 실패 시 기존 사진 보존, 재시도 후 같은 요청 키로 중복 사진을 만들지 않음.
- 연습·공연 취소: 기존 출석 삭제, 통계 제외, 사진 경고 제외, 일정은 취소 표시.

### 곡·자료

- 공연을 곡 없이 생성 → 기존 전체 곡에서 여러 곡 선택 → 순서 변경.
- 선택 창에서 새 곡 등록, 별도 곡 등록 시 공연 선택 또는 공연 미정.
- 같은 곡을 2개 공연에 연결했을 때 자료 공유. 한 공연에서 제거해도 다른 공연 연결 유지.
- 일반 단원은 공연 상세의 곡/순서만 보고 자료 URL은 API에서 받지 못함.
- 필기본 PDF/JPG/PNG/HEIC, 음원 MP3/M4A/WAV 업로드. 음원은 날짜별 축적.
- 파일 크기 0, 허용하지 않은 확장자, 서버 한도 초과, Notion 요금제 한도 초과, 대형 분할 업로드 중 실패를 확인한다.
- HEIC는 브라우저에 따라 인라인 표시가 안 될 수 있다. 원본 열기 경로와 실제 기기 표시를 확인한다.
- 곡별 최신 필기본만 확인 의무. 이전 파일과 확인 기록은 보존. 음원은 각 파일의 확인 필수 설정을 따름.
- 파일을 먼저 열지 않고 확인 완료 요청 → 409. 열고 완료 → 확인 시각 기록.
- 같은 학기/같은 파일은 공연이 여러 개여도 확인 1번, 배지 1건.
- 새 파트장·반주자도 현재 학기의 지난 공연 자료까지 확인 의무.
- 공연 미정은 확인 의무 없음. 취소된 공연에서만 쓰는 자료도 의무 없음.
- 새 학기 공연으로 연결하면 기존 확인을 재사용하지 않고 새 학기 확인을 요구.
- 지휘자에게 현재 대상 인원 분모와 미확인자 우선 목록, 확인 시각이 보임.

### 출석

- 기존 사전 입력·시작 후 본인 수정 금지·지각 사유/도착 시각 규칙 유지.
- 활동 반주자가 있을 때만 반주자 파트 확인 필수. 반주자 파트 확인은 지휘자만 가능.
- 파트 확인 후 출석 변경 시 해당 파트 확인 해제.
- 모든 필수 파트 확인 전 마감 → 409. 마감 시 미입력자 결석을 노션에 저장한 후 마감 상태 반영.
- 재오픈 후 이전 학기 출석 수정 가능. 취소/행정 일정에서는 출석 API 거부.
- 출석 현황의 5초 자동 폴링은 제거했다. 상단 새로고침/출석 변경 후 다시 노션에서 로드한다.

### 재정·학기

- 기존 분류 선택지와 수식을 유지하고 일반 단원도 담당자·비고까지 조회.
- 총무만 항목 생성/수정/삭제. 삭제는 Notion archive API이며 앱에 삭제 상태/별도 삭제 이력을 만들지 않음.
- 최초 기존 장부 행에는 2026년 2학기 관계를 저장한다. 이후 Notion에서 직접 만든 미지정 행은 현재 학기에 배정한다.
- 처음 2026년 2학기. 단장만 마감 가능. 다음 학기 이름 확인 후 자동으로 2027년 1학기 생성.
- 전환 시각보다 나중에 시작하는 일정을 옮긴다. 진행 중인 행정/이미 시작한 일정은 이전 학기 유지.
- 옮겨진 일정에 미리 기록한 출석도 새 학기 관계로 이동한다.
- 전환의 각 저장 단계에서 실패시켜 재실행: 다음 학기 중복 생성/이중 마감/이동 누락이 없어야 함.
- 학기별 Notion 보기 생성에 실패한 뒤 재시도해 중복 보기가 생기지 않는지 확인한다.
- 전 학기 확정 잔액을 총무가 이월 확정. 모든 기간 합계에서 이월을 다시 수입으로 더하지 않음.
- 이전 장부 수정으로 잔액 변경 시 재확인 알림. 총무가 재확정하기 전 이월금 불변.
- 이전 학기 경고는 해당 학기를 선택할 때만 보임. 과거 기록은 잠금 없이 현재 역할 권한으로 수정.

### 저장·실패·동시성

- 페이지 로드에서 Notion을 다시 조회하며 역할 변경 반영.
- Notion 저장 실패를 클라이언트 성공으로 표시하지 않음. 폼/선택 파일이 남고 재시도 가능.
- 서버가 저장 후 응답만 잃은 create/upload 재시도에서 같은 앱 키가 중복을 방지.
- 노션 조회 실패 시 마지막 성공 snapshot에 stale 표시, 편집 차단. 캐시가 없으면 재시도 화면.
- 일반/지휘/행정 계정을 교대 로그인해 이전 계정 snapshot이 노출되지 않는지 확인.
- 같은 이벤트/곡/장부를 두 창에서 수정한 경우 edited_at 충돌 응답을 확인.
- Notion에는 트랜잭션/CAS가 없으므로 직접 Notion 편집과 앱 쓰기의 아주 짧은 경쟁 구간은 별도 위험으로 검토한다.
- 많은 관계(25개 이상), 페이지 100개 이상, 여러 장 사진, 큰 JSON 속성의 페이지네이션을 확인한다.
