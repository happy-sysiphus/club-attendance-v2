## 결론

**현재 상태로 `main` 머지·배포 금지.** 설계와 권한 구조는 견고하나 구현이 한 번도 실행된 적이 없고, 실행 시 막히는 지점이 남아 있다.

구현자가 인수인계 문서에서 명시한 대로 테스트·구문 검사·브라우저 실행·실제 노션 호출을 **전혀 수행하지 않았다.** 이 리뷰는 그 공백을 정적 분석과 기존 테스트 실행으로 메운 것이며, 실제 노션 API 호출은 이 리뷰에서도 하지 않았다(실제 데이터 보호).

## 수정 현황 (2026-09-07, 리뷰 당일 반영)

사용자 결정: "노션이 DB인 앱"이므로 노션 계층이 서지 않으면 앱도 서지 않는 fail-closed는 설계다. 그 관점에서 **조용히 열리는 실패**(명단 오타 단원 소실, 속성 형식 불일치 시 권한 소멸, 영구 오류를 "다시 시도"로 위장)만이 진짜 결함이라 그쪽을 고쳤다.

### ~~1. 실제 회계장부 ID가 하드코딩 기본값~~ → 의도된 동작 (사용자 확인으로 제외)

`app/operations_store.py:109`의 기본값 `4379fa3860c94a498dbae5e444dd9afd`는 스펙 §8 "기존 장부에 학기 속성을 추가해 계속 사용한다"와 인수인계 §131 "최초 기존 장부 행에는 2026년 2학기 관계를 저장한다"에 따른 **정상 동작**이다. 첫 실행 시 실제 장부에 `학기`·`앱 키` 열이 추가되고 기존 행 전부에 학기 관계가 기록되는 것이 사양이다. 초기 리뷰가 이를 배포 차단으로 분류한 것은 오류였다.

남는 것은 개발 중 주의사항 하나뿐이다: **완성 전 코드를 실제 장부에 대고 실행하지 않는다.** 현재 사용자 셸에 `NOTION_TOKEN`·`NOTION_PARENT_PAGE_ID`가 설정돼 있어 이 폴더에서 `python -m app.main`을 실행하면 즉시 실제 장부가 바뀐다. 개발·테스트 중에는 검증용 장부 사본을 `NOTION_LEDGER_DATABASE_ID`로 지정한다. 이는 코드 수정 사항이 아니라 운영 절차다.

### 2. 학기 DB의 빈 행 하나가 앱 전체를 500으로 정지 ✅ 수정됨

**수정(2026-09-07):** `operations.py` `load()`에 다른 kind와 동일한 필터 추가 — `title`·`year`·`half`가 비어 있는 학기 행은 초안으로 간주해 제외한다. 필터 후 학기가 0개면 기존 로직대로 2026년 2학기를 생성한다.

`app/operations.py:94-97, 189, 351`

`load()`는 events·songs·materials·ledger의 미완성 행을 걸러내면서(코드 주석: "Notion permits unfinished blank rows") **semesters만 필터하지 않는다.** 노션 '학기 관리' DB에서 새 행을 한 번 누르면 `year`/`half`가 `None`이 되고:

```python
"semesters": sorted(data["semesters"], key=lambda s: (s["year"], s["half"]), reverse=True),
# TypeError: '<' not supported between instances of 'int' and 'NoneType'
```

`current()`는 `state=='active'`만 보므로 정상 동작해 `NotionUnavailable`로 잡히지 않고, `HTTPException`도 아니라 503 stale 폴백도 타지 못한다. **유일한 상태 엔드포인트 `/api/state`가 모든 사용자에게 500이 되고 앱 내부에 복구 경로가 없다** — 노션에서 직접 행을 지워야 한다. `close_semester`의 `int(old["year"])`도 같은 이유로 실패.

**수정:** `load()`에 semesters 필터를 다른 kind와 동일하게 추가.

`app/operations_routes.py:250-287`

### 4. 실재 미확인 노션 API가 모든 요청의 필수 경로 🟠

`app/operations_store.py:218-267`, 호출부 `app/operations.py:104-106`

`modern()`이 `Notion-Version: 2026-03-11`로 `GET /v1/databases/{id}`, `GET /v1/views`, `POST /v1/views`를 직접 호출한다. **이 API 버전과 최상위 `/v1/views` 엔드포인트의 실재 여부를 이 리뷰에서 확인하지 못했다(불확실).**

실재 여부와 무관하게 구조가 문제다: `ensure_semester_views`가 `Operations.load()`에서 학기마다 매 요청 호출되고, 실패하면 `httpx.HTTPError` → `NotionUnavailable`로 올라간다. 쓰기 경로(`execute` → `context` → `load`)가 이 예외를 잡지 않으므로 **로그인·일정·출석·회계 등 모든 API가 영구 503**이 된다. 기능 플래그도 degrade 경로도 없고, 배포 직후 첫 요청은 캐시가 없어 무조건 실패한다.

또한 view 필터를 `{"property": <prop_id>, "relation": {"contains": ...}}` 형태로 보내는데 이는 `databases.query` 필터 문법이며 view 필터 DSL과 동일하다는 근거가 없다(불확실).

**수정:** 학기별 보기 생성을 선택 기능으로 격리한다. 실패해도 `load()`가 계속 진행되도록 예외를 삼키고 로그만 남긴다.

### 5. 사진 2장째 업로드·삭제가 거부될 가능성 🟠 (실측 필요)

`app/operations_routes.py:289-297` (`writable_files`), 호출부 `163, 205`

노션에 업로드된 파일은 조회 시 `type="file"` + 만료되는 서명 URL로 내려온다. `writable_files`는 이를 그대로 `{"type": "file", "file": {"url": ...}}`로 재구성해 `pages.update`의 files 속성에 다시 써넣는다. files 속성 쓰기는 `external` / `file_upload` 객체만 받는 것으로 알려져 있어 **400 → 503이 될 공산이 크다.**

그렇다면 합의 스펙 §5의 핵심 흐름(사진 여러 장, 교체, 서로 올린 사진 삭제)이 **두 번째 조작부터 전부 실패**한다. 최악의 경우 기존 사진 참조를 잃은 채 새 목록으로 덮어써 이전 업로드가 페이지에서 떨어져 나간다.

두 리뷰 에이전트가 독립적으로 같은 지점을 지목했다. `materials`는 항상 새 행에 첨부 하나만 쓰므로 이 경로를 타지 않는다(**사진만** 위험).

**필수 조치:** 검증용 워크스페이스에서 사진 2장 연속 업로드 → 1장 삭제를 실제로 실행해 확인. 아울러 서명 URL을 프런트에 직접 주지 말고 서버 리다이렉트 경로를 두어 매번 새 URL을 받게 한다(현재 캐시된 URL은 1시간 후 만료).

### 6. 모든 화면 조작이 3~6초 걸린다 🟠

`app/operations.py:88-118`, `app/operations_store.py:40`, `app/operations_routes.py:52-56`

**단원 30명 규모 기준으로 재계산한 결과다.** 동시 접속이 아니라 **매 요청의 고정 지연**이 문제다.

`execute()`도 `snapshot()`도 매번 `load()`를 부르고, `load()`는 semesters·songs·events·materials·acknowledgements·attendance·ledger 전량 + roster를 읽는다. `store.call()`이 호출당 0.35초 스로틀을 건다.

| 시점 | 노션 호출 수 | 요청당 지연 |
| --- | --- | --- |
| 학기 초 (출석 기록 적음) | 약 8회 | 약 2.8초 |
| 학기 말 (30명 × 30연습 = 900행 → 출석만 9페이지) | 약 16회 | 약 5.6초 |

앱을 열 때도, 출석을 입력할 때도, 회계를 볼 때도 매번 이 시간이 붙고 **학기가 진행될수록 선형으로 늘어난다.** 인원이 30명이든 5명이든 동일하다.

동시 접속 영향은 30명 규모에서는 제한적이다. 전역 `RLock`으로 직렬화되므로 연습 직전 5~10명이 몰리면 마지막 사람이 15~30초를 기다리지만, 30명이 동시에 누르는 상황은 현실적이지 않다. **초기 리뷰에서 "사실상 사용 불가"로 쓴 것은 60명·1,800행 가정에 기반한 과장이었다.**

`snapshot`의 현황판 계산(`operations.py:197-198, 411-430`)도 30명 기준으로는 30일정 × 30명 × 900행 ≈ 81만 회 반복으로, 파이썬에서 0.1~0.5초 수준이다. 노션 왕복 시간에 묻히므로 우선순위는 낮다.

**다만 인원과 무관하게 심각한 것이 하나 있다:** 대용량 업로드가 전역 잠금을 점유한다(#14). 지휘자가 음원 하나를 올리는 동안 **모든 단원의 출석 입력·조회가 정지**한다. 30명이어도 그대로 발생한다.

**해결 방안 (합의됨):**

**(a) 스냅샷 캐시 + 쓰기 후 캐시 직접 갱신** — 고정 지연과 학기 내 증가를 함께 해소

```python
# operations_store.py
self._snapshot, self._snapshot_at = None, 0

def load(self, force=False):
    if not force and self._snapshot and time.monotonic() - self._snapshot_at < 15:
        return self._snapshot
    data = {kind: self.read(kind) for kind in KINDS}      # 기존 코드
    self._snapshot, self._snapshot_at = data, time.monotonic()
    return data

def save(self, kind, page):
    saved = ...                                           # 기존 노션 쓰기
    if self._snapshot:                                    # 재조회 대신 캐시를 직접 갱신
        rows = self._snapshot[kind]
        rows[:] = [r for r in rows if r["id"] != saved["id"]] + [saved]
    return saved
```

- 조회는 0초. 쓰기는 노션 쓰기 1회만(재조회 없음).
- 처음 검토한 "쓰기 시 무효화" 방식은 **부족하다** — 출석 입력마다 다음 요청이 전량 재조회하므로 연습 직전 쓰기가 몰리면 학기 말 5.6초가 그대로 남는다. 캐시를 직접 갱신해야 재조회가 사라진다.
- 전량 조회는 기동 직후·15초 TTL 만료·상단 새로고침(`force=True`)에서만 일어난다. 이때만 학기 말 5.6초를 낸다.
- 앱 안에서 한 변경은 즉시 반영. 노션에서 직접 고친 건 최대 15초 뒤 반영. 스펙 §10의 "조회 실패 → stale 표시·편집 차단"은 그대로 동작한다.
- `delete()`도 같은 방식으로 캐시에서 제거한다.

**(b) 출석 조회에 학기 필터** — 학기를 넘어가며 쌓이는 것만 막는다

`databases.query`에 `학기` relation 필터 하나. 2학기가 1학기 900행을 다시 읽지 않게 된다. **단, 한 학기 안에서 0→900행으로 느는 것은 못 막는다.** 그건 (a)가 담당한다. (a) 없이 (b)만 하면 학기 말 5.6초는 그대로다.

**(c) 파일 업로드를 잠금 밖으로** — 인원 무관, 영향 가장 큼 (#14와 동일)

노션 파일 업로드는 2단계라 자연스럽게 나뉜다:

```
[잠금 밖]  파일 바이트 → 노션 file_upload API → file_upload_id 획득   (수 초~수 분)
[잠금 안]  file_upload_id를 페이지 속성에 붙이는 save()               (0.35초)
```

`operations_routes.py:167`의 업로드 라우트에서 `upload()`를 `execute()` **앞**에서 호출하고, 결과 id만 `execute()`에 넘긴다. 업로드 중에도 다른 사람의 출석 입력은 그대로 통과한다.

**우선순위:** (c) → (a) → (b). `attendance` 인덱싱과 `boards` 지연 계산은 30명 규모에서 후순위.

## 실제 노션 데이터 위험

첫 실행 시 실제 워크스페이스에 발생하는 변경. 1~3은 **사양대로의 변경**이며(사용자 확인), 되돌리려면 노션에서 수동 삭제해야 하므로 완성 전 코드로는 실행하지 않는다:

1. **실제 26-2 회계장부**에 `학기` relation·`앱 키` 열 추가, 학기 미지정 **전 행**에 학기 관계 기록 — 스펙 §8·인수인계 §131.
2. **명단 DB**에 `행정 직군` select 열 추가 — 스펙 §2.
3. **기존 출석 기록 DB**에 열 7개 추가 — 단 `날짜`·`연습명`이 빠져 신규 행이 반쪽이 되는 #18은 별도 문제.
4. 총무 삭제가 `pages.update(archived=True)`로 실제 행을 노션 휴지통으로 보냄. 앱 쪽 확인 절차·되돌리기 없고 30일 후 복구 불가.
5. SQLite 캐시가 없는 상태에서 노션 DB 제목을 바꾸면 재발견 실패 → 부모 페이지에 **같은 역할의 빈 DB 중복 생성**, 기존 데이터는 옛 DB에 고립.
6. 사진 files 왕복이 거부되면 이전 업로드가 페이지에서 떨어져 나갈 수 있음(#5).

## 검증 공백

옛 테스트 51개는 노션 미설정 503으로 전부 실패하며 **삭제 대상**이다. 삭제하면 신규 1,362줄에 **자동 검증이 0개**가 된다. 인수인계 문서가 권한 신규 테스트는 작성되지 않았다.

- 빈 학기 행·명단 파싱 실패 행 등 **미완성 노션 데이터** 방어(#2, #9, #10, #12).

## 잘 구현된 부분

정적 분석으로 확인한 사실이며, 아래는 수정 대상이 아니다.

- **권한 매트릭스가 버튼 숨김이 아니라 전 엔드포인트 서버 검사로 강제된다.** 지휘 일정=conductor, 행정 일정=head, 사진=head/publicity, 장부·이월=treasurer, 학기 마감=head, 자료 등록·수정·삭제=conductor, 자료 열람=is_music, 확인=is_recipient. `role`/`part`와 `admin_role`이 독립 필드라 겸임(파트장+총무 등)이 자연스럽게 두 권한을 모두 갖는다(스펙 §2-18 충족).
- **출석 규칙 5종 모두 정확**: 지휘자 제외, 반주자는 일반 단원과 동일 취급, 반주자 파트 확인은 지휘자만, 파트 확인 후 출석 변경 시 해당 파트 확인 해제, 필수 파트 미확인 마감 409.
- **학기 전환이 멱등**: 앱 키(`semester:YYYY:H`) 기반 create-dedupe + `transition_at` 고정 cutoff + "새 학기 먼저 활성화 후 이전 학기 마감" 순서 덕에 중간 실패 후 재실행해도 중복 생성·이중 마감·활성 학기 0개가 발생하지 않는다(#2의 `year=None` 케이스 제외).
- **이월금이 장부 행이 아니라 학기 속성에 저장**되어 전체 기간 합계에 이중 가산되지 않는다. `carry_needs_confirmation`이 최초 확정과 이전 학기 수정 후 재확정을 모두 잡는다(스펙 §8-106,107 충족).
- **자료 확인 의무 로직 정확**: 최신 필기본만 대상, 취소·공연 미정 곡 제외, 학기별 ack 키로 같은 학기 같은 파일 1회, 열람 없이 확인 요청 시 409.
- **기존 회계장부 수식·선택지 보존**: `databases.update`가 전체 교체가 아니라 부분 업데이트(`properties=missing` / `additions`만 전송)이며, `LEDGER` 매핑에 수식 열이 없어 쓰기 시도 자체가 없다.
- **페이지네이션 전부 구현**: `databases.query`(100행), `blocks.children.list`, 25개 초과 relation의 `pages.properties.retrieve`.
- **저장 멱등키**: create 직전 앱 키로 조회해 응답 유실 후 재시도의 중복 생성을 막고, 파일 업로드도 사진은 `stored_name`, 자료는 `key`로 이중 방어.
- **SDK 시그니처 일치**: `notion-client` 2.4.0의 실제 시그니처(`pages.properties.retrieve`의 page_size/start_cursor, `pages.update`의 archived, `databases.update`의 properties)와 맞고 `HTTPResponseError.status`도 실재.
- **cross-module 참조 전부 유효**: `db.now_kst`, `db.to_kst_naive_iso`, `db.VOCAL_PARTS`, `rules.*`, `auth`·`config`, store의 8개 메서드와 `execute()` 콜백 시그니처가 실제 정의와 일치. TODO·`pass`·빈 함수 본문 없음.
- **재발견 로직**: 부모 페이지 자식 스캔으로 기존 DB를 찾아 재배포마다 새 DB를 만드는 이전 문제는 (제목이 그대로인 한) 막았다.
- **프런트 stale 처리**: `api.js`의 `setReadOnly`가 조회 실패 시 GET·인증 외 요청을 차단하고, 출석 폼도 `getState().stale`로 잠긴다(스펙 §10-127 충족).
